## 已确认问题

### R1 · P1 · 编辑已有入口端口会使整个节点停止更新流量

- 位置：[协议编辑](../../../internal/sbctl/protocol_management.go) 229–242 行；[账本身份检查](../../../internal/sbctl/statistics_ledger.go) 60–67 行。
- 触发：一个入口已被采样，然后通过现有协议编辑功能改变监听端口，保留原标签。
- 原因：维护流程允许修改端口并完成重启；账本却将 `(scope,key)` 对应的协议、端口固定为不可变身份。后续每次采样都会抛出 `STATS_IDENTITY_CHANGED`。
- 影响：异常回滚整个采样事务，其他入口及用户的新计数也不再提交；旧导出文件继续存在，稍后显示过期。仅重启采集器不能解决身份冲突。
- 验证：`TestReviewPortEditFreezesLedger` 先建立账本，再执行实际维护领域逻辑修改端口；维护成功，下一次采样报错且序号不变。代理引擎使用 fake，没有启动真实容器。
- 建议：统一协议编辑与统计身份策略。可为端口变化建立新统计代并保留旧记录，或明确将端口作为可变元数据并同步调整中心校验；在完成迁移前应阻止会破坏采集的编辑。补上“已有流量→编辑端口→继续采集和同步”的集成回归。

### R2 · P1 · 维护生效后丢失回执，再禁用用户，会形成恢复死锁

- 位置：[维护恢复前置检查](../../../internal/sbctl/node_actions.go) 37–48 行；[授权请求生成](../../../internal/sbctl/worker.go) 53–65 行；[节点绑定检查](../../../internal/sbctl/agent.go) 128–131 行。
- 触发：协议维护已经在节点保存新模板，但 SSH 响应丢失，主控将任务标为失败；随后管理员禁用用户。
- 原因：主控仍用旧 `template_hash` 生成撤销请求，节点拒绝；此时重试原维护任务，又会因撤销 outbox 未完成而在发送恢复 RPC 前返回 `NODE_BUSY`。节点已有的幂等回执无法被取回。
- 影响：正常重试路径不能恢复主控绑定，也不能完成节点撤销。订阅链接可以被吊销，但已交付凭据在节点上可能继续有效；需要额外维护介入。
- 验证：`TestReviewLostMaintenanceReplyBlocksRevocation` 用故障注入模拟远端提交和响应丢失，确认后续撤销不能完成、维护重试被阻止且没有再次发送恢复 RPC。未在真实节点制造故障。
- 建议：把“查询原请求的持久回执并对账”与“发起新维护变更”区分，允许恢复先完成绑定同步，再优先执行最新撤销；增加这两个动作交错的故障测试，不能简单跳过所有互斥检查。

### R3 · P2 · 被新版本替代的未执行请求会永久阻塞节点维护

- 位置：[接收请求](../../../internal/sbctl/agent.go) 153–172 行、[仅执行最新请求](../../../internal/sbctl/agent.go) 176–185 行；[维护检查](../../../internal/sbctl/protocol_management.go) 326–329 行；重新绑定的类似检查在 `node_inspection.go` 360–367 行。
- 触发：版本 2 已接收但尚未执行，版本 3 随即到达并验证完成。
- 原因：旧版本 2 仍保留 `accepted` 状态；执行器以后只读取最新版本，维护却检查所有历史请求是否终结。
- 影响：即使最新授权已成功，重启及协议维护仍返回 `NODE_BUSY`，等待或重试不会清除这个历史阻塞。
- 验证：`TestReviewSupersededPendingBlocksMaintenance` 确认版本 3 为 `verified`、版本 2 为 `accepted`，维护重启失败。
- 建议：在新版本取代旧意图时持久标记旧请求为 `superseded`，同时保留仍用于撤销验证的历史文档；对现存历史状态提供安全修复路径。

### R4 · P2 · 更换不存在的账号名即可绕过登录入口的资源限流

- 位置：[登录限流和密码校验](../../../internal/sbctl/security.go) 110–129 行。
- 触发：同一来源连续使用不同的不存在账号名提交登录。
- 原因：限流键为 `账号名 + 来源`，只有失败后才记数；每个新名字都进入 Argon2id 运算，每次配置为 64 MiB 内存，且没有全局哈希并发上限。
- 影响：能够访问登录入口的请求方可以持续消耗 CPU/内存；高并发还可同时越过同一键的读后写检查。这里只确认限流缺口，没有压测或制造服务不可用。
- 验证：`TestReviewLoginLimitBypassByName` 同一来源用 12 个不同名字，全部进入密码校验并返回 `LOGIN_FAILED`，没有触发 `LOGIN_RATE_LIMIT`。
- 建议：在昂贵哈希前加入原子的来源/账号多维限流及并发预算。反代部署时仅信任明确代理的客户端地址，不能直接信任任意转发头。
