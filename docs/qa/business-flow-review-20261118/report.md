审查范围：节点接管与检查、协议入口、用户授权、订阅生成、配置同步、流量统计、权限与 SSH 边界、任务恢复、部署和既有单节点验收。

## 一、先给结论

### 1.「检查节点」不是从用户客户端发起的真实代理连接

截图里的「检查节点」任务由主控 worker 通过 SSH 调用受管 VPS 的固定 `diagnose` 动作，再用独立统计账号读取采样快照。诊断动作会读取 Compose、运行容器、镜像摘要、配置挂载、启动守卫和 sing-box 版本。主控随后确认统计采样时间不超过 30 秒。

这条路径没有启动临时 sing-box 客户端，也没有通过 AnyTLS、TUIC 或其它协议入口发起代理请求。因此截图里的：

- 「通过 · SSH 与容器」
- 「通过 · 运行绑定」
- 「通过 · 统计通道」

只能证明管理通道、容器绑定和统计采样正常。界面任务状态显示「已完成」也可能只是任务执行完成，结果中的 `ready` 仍然是 `false`。检查结果需要展开查看，不能把「已完成」直接理解为代理可用。

真正的协议拨测发生在以下路径：

- 节点接管完成后，节点执行器使用保存的系统探针凭据验证受管入口。
- 用户授权发布后，节点执行器验证新增凭据和保留的系统探针。
- 撤销凭据时，节点执行器验证旧凭据请求失败，再用有效探针做对照。
- 协议变更、配置变更或受控重启完成后，节点执行器验证登记探针。

节点上的 `DockerEngine.Probe` 会启动一次临时 sing-box 客户端容器，连接节点公网地址和入口端口，通过本地 SOCKS 代理请求 `https://www.gstatic.com/generate_204`，并在正向 UDP 探测中向 `1.1.1.1:53` 发 DNS 查询。这个验证发生在受管 VPS 上，不能证明用户手机或电脑所在网络、客户端导入过程和客户端实际策略都可用。

### 2.为什么 `anytls-in` 不能停用或删除

当前实现把节点登记的入口保存为 `NodeSettings.Endpoints`。接管校验要求恰好两个入口，并且必须分别是 AnyTLS 和 TUIC。授权、订阅和系统探针都根据这组登记入口工作。协议变更代码因此对登记入口的 `disable` 和 `delete` 返回 `PROTOCOL_REQUIRED`，前端也不显示这两个动作。

这个保护与入口排在第一行无关，也与当前授权用户数无关。截图显示授权用户为 0，只表示目前没有活跃的 sbctl 业务用户。当前实现把系统探针保存在受管入口上，又没有探针退役流程，所以入口不能靠“用户数为零”直接删除。节点登记、配置同步、授权生成和订阅生成仍然引用这组入口。

### 3.「协议入站」不是节点管理的必需品，但它是客户端连接的必需品

SSH 管理地址只负责管理 VPS，不能替代代理监听端点。若要让用户通过 sing-box、Surge 或 Mihomo 使用节点，节点必须有一个客户端能识别的协议入口、监听端口、服务器地址、TLS 参数和用户凭据。

因此应把两个概念拆开：

- **节点管理绑定**：容器、配置目录、镜像、运行守卫、SSH 管道、统计通道。它不应强制要求 AnyTLS 或 TUIC。
- **客户端服务入口**：为用户提供实际代理连接的协议入站。它可以是零个、一个或多个，取决于该节点是否要承载用户流量和要支持哪些客户端协议。

保留“每个用户独立授权”和“每个用户独立订阅”时，订阅仍然需要至少一个可发布且可验证的客户端入口。没有任何可用入口的节点可以被管理、检查、统计和维护，但不应被选为用户授权目标，也不应生成空的用户订阅。

这意味着当前的固定“两入口模型”是现有代码的架构约束，不是 SSH 管理的技术必然性。按你的要求，产品目标应改为：

- 允许无客户端入口的管理节点接管和运行检查。
- 允许只有一种受支持客户端协议的节点运行，例如只有 AnyTLS 或只有 TUIC。
- 用户授权仍按用户生成独立凭据，订阅仍按用户生成独立的 Surge 和 Mihomo 文件。
- 入口先通过当前配置版本的系统探针验证，才允许新增用户授权。新增用户凭据另行验证，通过后才进入该用户订阅。端口、SNI、ALPN、tag 等连接参数改变后，旧入口验证结果失效，必须按新配置版本重新验证。
- 入口停用或删除时，先进入入口退役流程，停止新分配和新发布，按受影响入口更新或吊销订阅，异步推进节点撤销，最后处理探针和入口。其它节点上的有效入口和订阅不应被连带吊销。没有探针退役流程前，不能声称没有业务依赖就可以删除。
- 若要支持 VMess、VLESS、Shadowsocks 等入口进入用户订阅，还需要同时补齐凭据模型、节点渲染、撤销探测、Surge 格式和 Mihomo 格式。当前代码的凭据校验和订阅渲染只支持 AnyTLS 与 TUIC。

审查后的入口解耦改造已经落到当前工作区。节点登记允许零个、一个或多个入口，凭据和统计使用稳定 `inbound_id` 隔离，入口退役通过版本化撤销回执推进。报告中“固定两入口”描述保留为审查基线，不再代表当前目标模型。1.14.x 自研统计接口也已接入节点采集，V2Ray API 和 Clash API 不再作为 sbctl 业务采集协议。

## 四、按影响排序的审查发现

### 架构差距 P1：固定 AnyTLS 加 TUIC 约束把节点管理和客户端服务耦合

**现象**

审查基线的接管、节点设置、探针、配置同步和授权都假设固定两入口。入口解耦改造已移除这一校验，只有一个入口或暂时没有用户入口的节点可以纳管。该改造仍需真实节点升级和无入口／多入口验收。

**影响**

在审查基线中，sbctl 不能把管理节点与代理服务入口分开表达。当前工作区已解除这一耦合，仍需完成发布和节点升级后验收入口退役、无入口节点和同协议多入口。

**最小改造方向**

把管理绑定与客户端入口分成两个状态。入口集合允许为空或只含一种当前支持的凭据协议。探针按实际受管入口生成。用户授权目标筛选必须排除没有通过当前配置版本系统探针验证的入口。入口退役使用独立流程处理授权、订阅和探针，而不是永久依赖删除保护。

### 界面语义 P2：检查任务的「已完成」容易被误读成「代理已通过」

**现象**

节点检查任务完成后，页面显示任务操作已完成，详情卡片才展示检查项。诊断结果可以带有 `ready:false`，而任务仍然以 completed 保存。

**影响**

管理员可能以为客户端连通性已经验证，实际上只确认了管理通道和统计采样。

**最小改造方向**

在界面把任务状态与检查结论分开显示。若 `ready:false` 或任一检查项失败，主状态应显示“检查完成，存在问题”。按钮旁应明确“此操作不发起客户端代理拨测”。

### 验收缺口 P2：既有真实拨测不是用户客户端拨测

**现象**

节点执行器在 VPS 上启动临时 sing-box，使用系统探针连接公网地址。它验证了从 VPS 到目标地址的协议路径。

**影响**

无法覆盖家庭宽带、移动网络、运营商 UDP、客户端版本、订阅导入和本地路由策略。

**已有边界**

既有文档明确写出真实代理认证和撤销探测由节点执行器执行，也明确写出测试不代表用户端 Surge/Mihomo 已人工导入。

**最小改造方向**

将“节点侧真实协议探测”和“客户端实机验收”设置为两个独立验收项。客户端实机验收需要在目标设备导入对应用户订阅，分别测试 AnyTLS、TUIC、TCP、UDP 和禁用后的失效。

### 部署验收缺口 P2：公网订阅反代仍有部署边界

**现象**

内部订阅服务监听 18101。历史验收发现现有站点只把根路径转发到 18100，`/s/` 会到管理 API 并返回页面不存在。仓库提供了独立 OpenResty 配置，但用户站点是否已经添加并验证不属于本轮源码证据。

**影响**

内部下载成功不等于公网订阅链接可用。用户可能在外部客户端看到 404。

**证据**

[主控说明中的反代边界](../../../ops/controller/README.md#L30-L36)

[管理验收中的公网订阅结论](../management-20261116/report.md#L37-L52)

**最小改造方向**

把内部 18101 下载和公网 `/s/<token>/<file>` 下载分别记录。发布验收中加入公网 URL 的 Surge 和 Mihomo 文件下载检查。

### 能力边界 P2：协议入口维护的统计覆盖面大于授权覆盖面

**现象**

入口维护和统计支持更多入口类型。统计会给无标签入口补标签，也会给本地用户补显示名。授权凭据和订阅渲染却只支持 AnyTLS 和 TUIC。

**影响**

协议目录显示“入口存在”和流量统计有数据，不能推出这个入口可以被 sbctl 用户授权或发布到客户端订阅。

**最小改造方向**

前端区分“可统计入口”和“可授权入口”。若要扩展授权协议，按协议补齐凭据校验、渲染、正向探测、撤销探测、订阅格式和安全审查。

### 状态耦合 P2：外部配置同步已经有保护，但入口删除会直接触发授权撤销

**现象**

节点 helper 记录配置事件序号和语义摘要。主控发现受管入口缺失、重复或无法唯一匹配时保存加密快照，标记冲突，撤销该节点凭据并暂停新增分配。

**影响**

这是安全的故障处理方式，但它把“用户入口被手工删除”和“节点管理配置发生变化”绑定为授权撤销。若未来允许管理节点无入口，需要增加“无用户入口、无须撤销”的明确状态。

**证据**

[配置同步冲突处理](../../../internal/sbctl/config_sync.go#L407-L471)

[受管入口匹配失败](../../../internal/sbctl/config_sync.go#L181-L225)

### 统计边界 P2：流量采集是 sing-box 原生连接统计，不是 VPS 网卡计数

**现象**

当前 collector 通过节点本机自研 Unix socket 读取 sing-box 1.14.x 的累计计数和连接增量，按运行 epoch、快照序号和连接序号写入账本。主控 sync 校验账本身份、序号和累计值不回退。旧节点在升级前仍可能使用历史 V2Ray API 路线，不能与新接口的连接明细能力混同。

**影响**

统计适合入口和命名用户累计，不表示网卡总流量，也不保证容器重启瞬间没有采样尾部缺口。历史验收已保留 gap 记录，没有宣称零损失。

**证据**

[节点 collector](../../../internal/sbctl/cli.go#L279-L306)

[账本 epoch 和缺口处理](../../../internal/sbctl/ledger.go#L29-L61)

[主控快照单调性校验](../../../internal/sbctl/traffic.go#L71-L128)

### 生产证据 P2：管理面 SSH 和 Web 防护边界清晰，但生产多节点证据不足

**已确认**

- 发布账号和统计账号使用不同密钥和固定远端命令。
- SSH 开启严格主机密钥校验和 `IdentitiesOnly`。
- 管理写请求要求会话、来源和 CSRF 校验。
- 控制库和流量库使用内嵌 SQLite，不依赖本机数据库服务。
- 节点维护保存计划，支持预检、回滚和中断恢复。

**仍未完成**

- 截至 2026-11-17 的验收记录，oraclesg 仍是原生 systemd sing-box，没有 sbctl-node、helper、统计 grpcurl 和兼容镜像。本次未连接生产复核。
- 多节点同时新增、撤销、失联恢复、流量对照和故障矩阵没有完整生产验收。
- 用户设备 Surge/Mihomo 实机导入没有验收证据。

## 六、建议的需求表述

把原来的固定约束改成下面这句话更准确：

> sbctl 通过 SSH、受限节点 RPC、容器运行绑定和统计通道管理 VPS。节点管理不要求固定协议入口。用户授权和用户订阅按用户独立生成。入口先通过当前配置版本的系统探针验证，才允许新增用户授权；新增用户凭据另行验证，通过后才进入该用户订阅。入口停用或删除时，先进入退役流程，停止新分配和新发布，按受影响入口更新或吊销订阅，异步推进节点撤销，最后处理探针和入口。当前用户授权和订阅协议先支持 AnyTLS 与 TUIC，新增协议必须同时补齐凭据、订阅、正向拨测、撤销拨测和配置同步。

这个表述同时保留了你要的两件事：

- 用户之间的授权和凭据仍然隔离。
- 订阅仍按用户分别生成。

它也移除了不必要的两项硬编码：

- 每个节点必须有 AnyTLS。
- 每个节点必须有 TUIC。

## 补充审查：7 项边界与改造要求

### 1. 入口删除必须先退役探针

当前节点本地保留系统探针，探针读取逻辑要求 AnyTLS 和 TUIC 探针都存在。代码没有提供“停用探针、验证旧探针撤销、清理探针文件、再删除入口”的退役流程。因此“没有业务依赖就可以删除”目前不是已实现行为，单纯放开删除按钮会留下系统探针依赖。

目标流程应为：

1. 入口进入 retiring 状态，立即停止新授权分配和新订阅发布。
2. 计算受影响的用户、任务和订阅。后续订阅版本只移除这个入口，保留用户在其它节点或其它入口上的有效配置。若用户已经没有其它有效入口，再吊销整份用户订阅。
3. 节点撤销异步推进。撤销用户凭据时保留同入口系统探针，用相同入口和参数验证旧用户凭据失败，并用该入口仍有效的系统探针作正向对照。
4. 整体退役任意入口时，完成该入口的用户凭据撤销验证后，清理该入口的系统探针和入口配置。无论节点是否还有其它入口，都不再用其它入口探针替代该入口的退役确认。使用对应版本的节点退役回执、活动配置和运行状态确认该入口已经删除，也不能把连接失败记为认证拒绝。
5. 保存可恢复的退役回执。超时或节点离线时保留 retiring 状态，禁止新分配并继续补偿。

当前代码已提供入口退役任务、入口级订阅撤下、凭据撤销绑定和活动配置回执。最后一个或非最后一个入口都必须用被退役入口自身的版本化回执、活动配置和运行状态确认删除，其他入口探针不能替代该确认。真实节点退役和失联补偿仍待验收。

### 2. 零个、一个和多个入口需要稳定身份

当前入口 tag 同时用于配置匹配、节点登记、订阅来源和部分统计归属。当前接管还要求恰好两个且协议不同，凭据唯一范围是用户、节点和协议。两个 AnyTLS 入口无法被当前模型无歧义区分。

改造必须引入不可变 inbound_id，并把 tag 作为可变的 sing-box 配置字段。

- 入口身份使用 node_id 加 inbound_id。
- 凭据身份使用 user_id、node_id、inbound_id、protocol 和 generation。
- 订阅节点使用 inbound_id 生成稳定名称，端口、SNI、ALPN、tag 作为当前参数。
- 修改端口、SNI 或 tag 是同一入口的编辑。修改协议或认证语义先退役旧入口，再创建新入口。
- 入口编辑、授权发布和外部配置同步用入口版本、节点版本、幂等请求和节点回执串联。主控 SQLite 事务不能单独保证节点文件已经完成。
- 超时或响应丢失时，只有在内容不变且没有更高版本取代时，才继续同一个 request_id 和 revision。目标变化、撤销状态变化或入口退役状态变化时，生成新请求和更高版本，节点拒绝过时请求，恢复或回滚不能覆盖较新的撤销／退役记录。
- 旧数据迁移为 anytls-in 和 tuic-in 生成一次稳定 ID，保留凭据 generation、指纹、撤销历史和订阅 revision。重复 tag、同协议多入口或不能唯一匹配的数据进入人工迁移状态。

这样才能表达无入口管理节点、单入口节点和多个同协议入口。入口先通过当前配置版本的系统探针验证，才进入新增用户授权选择。新增用户凭据另行验证，通过后才进入订阅。

### 3. 检查完成与节点可用分开显示

当前 node_jobs 的 completed 表示任务函数完成，diagnose 返回的 ready 和 checks 才表示检查结论。任务完成本身不等于协议可用，也不必然是后端错误。界面需要显式拆开管理通道、运行绑定、统计、节点协议拨测、订阅下载和客户端验证。

每项状态建议使用通过、失败、未执行和不适用，并保存检查时间、节点配置版本、入口版本、请求 ID 和证据摘要。无入口管理节点的协议拨测应为不适用，不能因此判定管理失败。界面同时显示任务完成和当前检查结论。

### 4. 订阅吊销与凭据撤销是两个状态机

当前 PublicStore.Revoke 删除订阅索引，后续下载返回 404。用户已经下载的 Surge 或 Mihomo 文件不会被删除。用户禁用时，节点撤销仍通过 outbox 异步下发。节点离线或撤销失败期间，旧凭据可能继续有效，直到新配置应用并完成负向验证。

应分别记录并展示：

- subscription_revoked_at
- node_revoke_pending_at
- node_revoke_applied_at
- node_revoke_verified_at
- revoke_blocked
- last_error 和 retry_after

当前 operation_targets 和节点请求回执已有部分状态基础，但没有完整展示这四个阶段。现有代码也没有独立证明已有连接何时断开。容器重建可能影响旧连接，不能替代“已有连接已断开”的单独验收。

恢复只沿用内容不变且仍是最新目标的 request_id、revision 和撤销指纹。目标已变化或被更高版本取代时，旧任务必须被节点拒绝，不能把已经撤销或退役中的用户、入口重新写回节点。这个恢复不变量应新增测试。

### 5. 真实拨测还需要更细的路径证据

源码中的临时客户端只配置目标协议 outbound，route final 指向该 outbound。HTTP 使用 socks5h，TLS 开启并使用入口 SNI，没有看到 skip-cert-verify 开启。UDP 请求也进入同一 final 路由。代码路径没有看到直连回退配置，但当前报告不应把这等同于完整安全证明。

待补证据包括：

- 记录唯一 outbound、route final、TLS server name 和证书校验选项。
- 在入口不可达、证书错误、代理拒绝和直连目标可达时确认不会直连回退。
- UDP 验证事务 ID、响应码、答案数量和代理路径。
- 撤销负测使用相同入口、SNI、目标和超时，并区分认证拒绝、TLS 错误、超时和断网。
- 负测后用有效系统探针作正向对照。

当前 Probe 只返回布尔值，负测得到 false 不能单独证明认证被拒绝。Verify 已有有效探针对照，但缺少面向回执的错误分类和证据记录。这里应标为待核查项，不能直接判定已有实现存在漏洞。

### 6. 客户端矩阵增加版本和验证层次

当前源码证明了 Surge 文本和 Mihomo YAML 的生成，没有证明目标客户端版本可以解析、握手或产生流量。历史节点回执记录 sing-box 1.12.9，没有 Surge 或 Mihomo 实机版本。

矩阵应区分平台、客户端和内核版本、配置生成、配置解析、握手、TCP、UDP。已知证据如下：

| 平台 | 客户端版本 | 生成 | 解析 | 握手 | TCP | UDP | 证据 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 节点 Linux | sing-box 1.12.9，历史回执 | 不适用 | 临时 JSON 启动 | AnyTLS、TUIC | HTTPS 204 | DNS 正向探测 | 节点拨测 |
| iOS 或 macOS | Surge 版本未记录 | 已生成 | 未验证 | 未验证 | 未验证 | 未验证 | 无实机证据 |
| Linux、Windows 或 macOS | Mihomo 版本未记录 | 已生成 | 未验证 | 未验证 | 未验证 | 未验证 | 无实机证据 |

只验证客户端声明支持的协议和传输组合。配置下载 200 或服务器侧探针通过，不能升级为客户端解析和握手通过。

### 7. 统计和部署结论带上时间与身份边界

统计链路已有 ledger_id、snapshot_seq、source_epoch、配置摘要和重复序列保护。相同序号内容变化会被拒绝，计数下降或入口消失会标记异常。这能防止一部分回放、回退和身份混淆，但不等于无漏计或无重复。epoch 切换和采样间隔仍可能产生 gap。

还需补测：

- 正常重启、程序升级和配置重载后 ledger_id 保持不变。
- 账本丢失或重建时生成新账本身份，进入重新登记或迁移确认流程，保存旧账本与新账本的关联记录。不能沿用旧 ledger_id 后把 snapshot sequence 归零。
- 相同 snapshot sequence 重放不重复入账。
- 入口删除再创建时，旧入口历史仍归旧 inbound_id，新入口必须使用新的 inbound_id。即使复用同名 tag 或同端口，也不能继承旧身份、旧凭据、旧撤销记录或旧流量，避免历史混账。
- 展示名、tag、端口和协议字段与稳定身份分离。

公网反代、oraclesg 接入、节点版本和客户端导入会随部署变化。报告中的这些事实应写为“截至对应历史验收记录，本次 2026-11-18 未连接生产复核”，不能直接当作今天的现状。

## 优先级重新分类

- 固定双入口是审查基线中的产品和架构差距，当前代码已改为零／单／多入口；优先完成双架构发布和真实退役验收。
- “任务完成”与“节点可用”混用是界面语义问题。
- 节点侧拨测不等于客户端互通，是验收覆盖缺口。
- 订阅吊销与凭据撤销的分离是安全状态机要求，应补充展示和恢复测试。
- 直连回退、TLS、UDP 路径和撤销失败分类是拨测证据缺口，当前不能据此直接判定已有漏洞。
- Surge 和 Mihomo 的版本、解析、握手及 TCP／UDP 实机验证是客户端兼容验收缺口。
- 统计单调性是完整性保护，不等于无损计量。公网反代和 oraclesg 只代表历史记录，本次没有生产复核。
